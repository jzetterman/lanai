# Snapshot naming implementation plan

Governing spec: [spec.md](spec.md). John accepted the revised spec after the three-round Grok stage-a cap on October 20, 2026, and the same day cut the panel's as-you-type character check (see the spec's closing note). Use **label** for the user-visible name and **identifier** for the UTC folder name; existing JSON `name` keys keep their identifier meaning.

This work builds on the Delete and panel copy changes, committed on branch `snapshot-delete`. Branch `snapshot-names` stacks on it, so the naming-only diff is `git diff snapshot-delete...snapshot-names`.

The Python helper owns the validation rule and its user-facing messages. It checks the rules in the listed order: invalid UTF-8 first, since the other rules need decoded text, and the first rule a label breaks is its reply. The panel does no validation of its own; it shows the message from a refusal.

| Rule key | Trigger | Message |
| --- | --- | --- |
| `invalid-utf8` | Invalid UTF-8 argv bytes | Use valid UTF-8 text. |
| `line-break` | CR, LF, U+2028, U+2029 | Use one line. |
| `angle-bracket` | `<` or `>` | Remove < and >. |
| `separator` | Other Unicode category Z characters except U+0020 | Use ordinary spaces. |
| `invisible` | Unicode category Cf | Remove unsupported invisible characters. Some emoji contain them. |
| `unsupported-character` | Other Unicode category C characters | Remove tabs, control characters and icon symbols. |
| `too-long` | More than 64 code points after edge trim | Use 64 characters or fewer. |

## Phase 1: name validation and storage

1. Write failing `test/snapshot.bats` cases in isolated storage for omitted, empty, and spaces-only labels as successful unlabeled snapshots with no `LABEL` and `label:null` in success JSON; and for trimmed, 64-code-point, leading `-`, and metacharacter labels as successful labeled snapshots. Use 64 four-byte emoji (256 bytes) to check the 257-byte metadata limit. Cover extra arguments, 65-code-point, invalid UTF-8 with its own refusal rule, forbidden Unicode categories, and `<` and `>` as refusals. Prove invalid input is refused before the operation lock, disk proof, or creation of a partial directory. Prove a successful labeled snapshot still uses its UTC folder name and contains a readable label. Inject a `LABEL` write failure and assert no completed snapshot is published. Before implementing the reader, add failing readback cases for legacy, missing, oversized, malformed, edge-spaced, and symlinked metadata; a `LABEL` directory and named pipe (with a timeout proving the poll cannot block); duplicate copies where the first has unreadable metadata and the second has a valid label; and duplicate valid copies where the first readable label wins. Assert each otherwise valid snapshot stays visible and available to Restore/Delete. Inject a metadata-helper failure and assert the snapshot path array still reaches the CLI and panel with an empty labels map.
2. Add `lib/snapshot-label.py` for the authoritative validation rule and message map above. `validate VALUE` writes one JSON object, either `{ "ok": true, "label": string|null }` or `{ "ok": false, "reason": "invalid-label", "rule": string, "message": string }`; invalid user input is a normal response, while a helper execution failure exits nonzero. Strictly decode `os.fsencode(VALUE)` as UTF-8 before categorizing, so surrogateescaped invalid argv bytes have their own rule under any locale. It trims only U+0020, CR and LF at the edges, returns an empty normalized label as a valid unlabeled result, and rejects nonempty invalid UTF-8, category C, category Z except interior U+0020, `<`, `>`, and more than 64 Unicode code points with the table's exact rule and message. `read PATH...` writes one JSON array of string-or-null labels in input order, so one Python process handles the complete path list per poll. The reader opens `LABEL` without following symlinks or blocking on a non-regular entry, verifies it is a regular file, reads at most 258 bytes, rejects anything longer than 257 bytes or with leading/trailing U+0020, permits at most one final newline, and applies the same nonempty rule. Invalid metadata yields null; it does not invalidate the snapshot. Use the helper with `python3` already required by image proof.
3. Update `cmd_snapshot` to accept zero or one optional label, validate before `lanai_flock`, pass a validated label to `snapshot_create`, and include `label` in its structured success reply (`null` when unlabeled) while keeping `name` as the UTC identifier. An invalid label returns `{ok:false, reason:"invalid-label", rule:<rule key>, message:<specific rule>}` so the panel can show the reason beside the initiating field; test that reply. If the validation helper fails, fail closed before disk access. `snapshot_create` writes `LABEL` only for a nonempty label in the partial snapshot after clone and manifest checks and before its final directory sync and rename; any write failure aborts publication. Adjust `snapshot_valid` to ignore only the top-level `LABEL` entry during install-file enumeration; restore continues to copy only manifest-listed install files. Leave UTC identifiers and `snapshot_find` unchanged.
4. Extend `cmd_snapshots` with a `labels` object keyed by UTC identifier while preserving the existing `snapshots` path array. Pass the complete validated path list to one `snapshot-label.py read` call. Iterate its results in path order; for duplicate UTC identifiers, keep the first readable label and skip invalid labels. The one resolved `labels[id]` value applies to every path with that identifier; an unlabeled identifier has no map entry. If the metadata helper fails, keep the path array and emit `labels:{}` so Restore/Delete remain available. Verify the failing phase-1 readback and visibility tests pass.
