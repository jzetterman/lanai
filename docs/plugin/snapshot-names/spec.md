# Name snapshots when they are taken

## Problem

The Snapshots panel identifies restore points only by UTC date and time. A user cannot tell which change each snapshot precedes without remembering when it was taken. This document calls the user-visible name a **label** and the UTC timestamp a snapshot **identifier**. The field shown to users remains `Snapshot name (optional)`.

## Requirements

- A user may enter an optional label before taking a snapshot from either the Snapshots section or the setup snapshot offer. `lanai snapshot` accepts zero or one label argument; extra arguments are rejected rather than joined. A label beginning with `-` is accepted as a literal argument without a `--` separator. An empty label keeps the current timestamp-only behavior. Labels are set only when a snapshot is taken; this feature does not rename existing snapshots.
- Only leading and trailing ordinary spaces (U+0020) and line breaks (CR, LF) are trimmed. An empty result, including spaces-only input, means an unlabeled snapshot. A nonempty label must be valid UTF-8 and contain 1–64 Unicode code points after trimming. Unicode `Other` (category C) and Unicode `Separator` (category Z) characters are forbidden, except U+0020 inside the label. `<` and `>` are also forbidden. This intentionally rejects invisible format characters such as the emoji zero-width joiner; feedback calls them unsupported invisible characters. An invalid label is rejected, never truncated or silently changed, with a reason before locking or reading the Windows disk; it creates no partial or completed snapshot. The panel does not check or change the draft while the user types or pastes. It submits the exact text, and the backend's rule-specific error appears beside the field after the attempt. The panel never submits a changed version as if it were the user's original label.
- A label is stored with the completed snapshot and survives panel or shell restarts. If a valid label cannot be written, the named snapshot fails and no completed snapshot is published. The UTC timestamp remains the snapshot's unique identifier and filesystem folder name. Restore and Delete still target that identifier. Two snapshots may share a label. Existing JSON `name` keys retain their UTC identifier meaning. CLI success JSON adds `label`, set to `null` for an unlabeled snapshot; `lanai snapshots` adds a `labels` object keyed by UTC identifier alongside its existing path array, resolving duplicate copies to one label per identifier and omitting unlabeled identifiers. In the panel model, new `user_label` carries the saved label while existing `label` keys keep their formatted date or restore-status meanings.
- The panel shows a saved label above its snapshot's UTC date and time. A long label wraps inside the panel without clipping the date or buttons. Restore and Delete buttons keep their short visible labels; their accessible names and active and unfinished restore statuses include both the saved label and UTC date/time. The visible confirmation question names only the action, because the row above it already shows the label and date. When equal labels share a displayed UTC minute, the date rows, accessible names, and restore statuses include seconds so those restore points can be told apart. Long confirmation wording wraps as text outside the buttons. Existing unlabeled snapshots continue to show their dates and work as before.
- A saved label is readable only when its metadata is a readable regular file, is not a symlink, decodes as UTF-8, holds one logical line with at most one final newline, has no leading or trailing U+0020, and follows the same nonempty label rules above. The reader checks at most 258 bytes and rejects any metadata longer than 257 bytes; a non-regular entry, including a folder or named pipe, is rejected without a blocking read. Missing or unreadable metadata, including a symlink or invalid content, does not hide an otherwise valid snapshot or prevent its restore or deletion. If copies with one UTC identifier have different metadata, the panel and CLI use the first readable label in the path order returned by `lanai snapshots`, skipping invalid labels; with none, they use the existing date/time display or a path-only CLI entry. A label is never used as a path or shell command. Older Lanai versions that require an exact snapshot folder contents will not list newly labeled snapshots after a downgrade; returning to a version with label support restores their visibility.
- Both the Snapshots section and the setup snapshot offer have a single-line field visibly labeled `Snapshot name (optional)`. The daily field has accessible name `Snapshot name (optional)` and the setup field has accessible name `Setup snapshot name (optional)` so they are distinct when shown together. Each field stays inside the panel at wide and narrow widths, is usable by keyboard, keeps its draft through periodic panel polls, section collapse/expand, and failed attempts, and clears it after a successful snapshot from that field only if it still equals the submitted draft. Enter in a focused field starts the same snapshot action as its adjacent button. The backend validation rule is authoritative; the panel must not transform a rejected input into a valid label. Take a snapshot remains enabled while a draft is invalid, and rule-specific feedback appears beside the submitting field after an attempt.

## Acceptance

Tests cover all three entry points, an omitted CLI label, extra arguments, a leading `-`, blank panel fields, spaces-only input, trimming a nonempty label before storage and length counting, the 64-code-point limit, invalid UTF-8, Unicode line separators and other forbidden characters, and a refusal that leaves no partial or completed snapshot and never opens the Windows disk. A failed metadata write also leaves no completed snapshot. Tests check that forbidden pasted and typed text is submitted unchanged, its rule-specific refusal appears beside the field, and the draft is kept. They cover legacy snapshots, persistence through `lanai snapshots` and panel reads, success JSON labels including `null` for unlabeled snapshots, and two snapshots with the same label. Tests also prove that missing, oversized, invalid, edge-spaced, symlinked, and non-regular label metadata falls back to the existing date/time display without losing restore/delete access or blocking a poll; that the first readable label wins between duplicate copies; and that a displayed label never replaces the timestamp target. A label containing path and shell metacharacters remains display data, never a path component or command. Both panel fields are checked for keyboard and distinct accessible names, Enter submission, draft survival across periodic polls, section collapse/expand, and failure, clearing after success without erasing a newer draft, rule-specific feedback, enabled Take a snapshot actions during invalid drafts, and bounds at narrow widths. Labeled Restore/Delete accessible names, confirmation wording, active and unfinished restore wording, same-minute duplicate disambiguation in all of those surfaces, and saved-label and confirmation-note wrapping outside the buttons are checked. No automated test touches the live Windows storage.
