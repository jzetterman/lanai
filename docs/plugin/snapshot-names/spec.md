# Name snapshots when they are taken

## Problem

The Snapshots panel identifies restore points only by UTC date and time. A user cannot tell which change each snapshot precedes without remembering when it was taken. This document calls the user-visible name a **label** and the UTC timestamp a snapshot **identifier**. The field shown to users remains `Snapshot name (optional)`.

## Requirements

- A user may enter an optional label before taking a snapshot from either the Snapshots section or the setup snapshot offer. `lanai snapshot` accepts zero or one label argument; extra arguments are rejected rather than joined. A label beginning with `-` is accepted as a literal argument without a `--` separator. An empty label keeps the current timestamp-only behavior. Labels are set only when a snapshot is taken; this feature does not rename existing snapshots.
- Only leading and trailing ordinary spaces (U+0020) and line breaks (CR, LF) are trimmed. An empty result, including spaces-only input, means an unlabeled snapshot. A nonempty label must be valid UTF-8 and contain 1–64 Unicode code points after trimming. Unicode `Other` (category C) and Unicode `Separator` (category Z) characters are forbidden, except U+0020 inside the label. `<` and `>` are also forbidden. This intentionally rejects invisible format characters such as the emoji zero-width joiner; feedback calls them unsupported invisible characters. An invalid label is rejected, never truncated or silently changed, with a reason before locking or reading the Windows disk; it creates no partial or completed snapshot. The panel does not check or change the draft while the user types or pastes. It submits the exact text, and the backend's rule-specific error appears beside the field after the attempt. The panel never submits a changed version as if it were the user's original label.
- A label is stored with the completed snapshot and survives panel or shell restarts. If a valid label cannot be written, the named snapshot fails and no completed snapshot is published. The UTC timestamp remains the snapshot's unique identifier and filesystem folder name. Restore and Delete still target that identifier. Two snapshots may share a label. Existing JSON `name` keys retain their UTC identifier meaning. CLI success JSON adds `label`, set to `null` for an unlabeled snapshot; `lanai snapshots` adds a `labels` object keyed by UTC identifier alongside its existing path array, resolving duplicate copies to one label per identifier and omitting unlabeled identifiers. In the panel model, new `user_label` carries the saved label while existing `label` keys keep their formatted date or restore-status meanings.
- The panel shows a saved label above its snapshot's UTC date and time. A long label wraps inside the panel without clipping the date or buttons. Restore and Delete buttons keep their short visible labels; their accessible names and active and unfinished restore statuses include both the saved label and UTC date/time. The visible confirmation question names only the action, because the row above it already shows the label and date. When equal labels share a displayed UTC minute, the date rows, accessible names, and restore statuses include seconds so those restore points can be told apart. Long confirmation wording wraps as text outside the buttons. Existing unlabeled snapshots continue to show their dates and work as before.
- A saved label is readable only when its metadata is a readable regular file, is not a symlink, decodes as UTF-8, holds one logical line with at most one final newline, has no leading or trailing U+0020, and follows the same nonempty label rules above. The reader checks at most 258 bytes and rejects any metadata longer than 257 bytes; a non-regular entry, including a folder or named pipe, is rejected without a blocking read. Missing or unreadable metadata, including a symlink or invalid content, does not hide an otherwise valid snapshot or prevent its restore or deletion. If copies with one UTC identifier have different metadata, the panel and CLI use the first readable label in the path order returned by `lanai snapshots`, skipping invalid labels; with none, they use the existing date/time display or a path-only CLI entry. A label is never used as a path or shell command. Older Lanai versions that require an exact snapshot folder contents will not list newly labeled snapshots after a downgrade; returning to a version with label support restores their visibility.
- Both the Snapshots section and the setup snapshot offer ask for the name after the user clicks Take a snapshot, the same way Restore and Delete ask before they act:
  - **Open.** The first click starts no snapshot. It opens a single-line field visibly labeled `Snapshot name (optional)` with keyboard focus in it, turns that button into `Save snapshot`, and shows Cancel beside it. Only one prompt is open at a time: opening the daily or setup prompt closes the other one and disarms Restore and Delete, and arming Restore or Delete closes the prompt. The buttons beside it, such as Continue without a snapshot and Show details, stay as they are.
  - **Submit.** Save snapshot, or Enter in the open field, starts the snapshot with the field's exact text. Both work only while the snapshot action is enabled, so neither starts a second snapshot while the prompt's own snapshot runs. Save snapshot remains enabled while a draft is invalid.
  - **While its snapshot runs**, from submission until its job ends or its launch fails, including polls before the job record appears: the prompt stays open, its field stays editable, and Cancel is hidden, because Cancel does not stop a snapshot.
  - **Close.** The prompt closes and keeps its draft on Cancel, on Escape while keyboard focus is in the open prompt (its field, Save snapshot or Cancel), on closing the panel, on collapsing the Snapshots section (daily prompt only), when its action is hidden, and when the action is disabled while no snapshot from this prompt is running, for example when Windows starts or another job begins. Escape and closing the panel work even while its snapshot runs, and a second Escape closes the panel. It stays open after any failed attempt and closes after a successful snapshot from it. When it closes with keyboard focus inside it, focus moves to Take a snapshot when it is shown and enabled, otherwise to the panel.
  - **Feedback.** The backend validation rule is authoritative; the panel must not transform a rejected input into a valid label. Rule-specific feedback appears beside the submitting field after an attempt. A refusal that arrives while its prompt is closed, for example when the user closes the panel right after Save snapshot, reopens that prompt with its draft and the refusal once its action is shown and enabled, unless another prompt is open or Restore or Delete is armed. Reopening moves no focus and starts nothing. A refusal that cannot reopen its prompt stays with its draft and shows when the user opens the prompt. A refusal clears on the next attempt.
  - **Drafts, names and layout.** Each field keeps its draft through periodic panel polls, section collapse/expand, a closed prompt and failed attempts, and clears it after a successful snapshot from that field only if it still equals the submitted draft. The daily field has accessible name `Snapshot name (optional)` and the setup field has accessible name `Setup snapshot name (optional)`, so a screen reader says which prompt is open. Each field, with its Save snapshot and Cancel buttons, stays inside the panel at wide and narrow widths and is usable by keyboard.

## Acceptance

Tests cover all three entry points, an omitted CLI label, extra arguments, a leading `-`, blank panel fields, spaces-only input, trimming a nonempty label before storage and length counting, the 64-code-point limit, invalid UTF-8, Unicode line separators and other forbidden characters, and a refusal that leaves no partial or completed snapshot and never opens the Windows disk. A failed metadata write also leaves no completed snapshot. Tests check that forbidden pasted and typed text is submitted unchanged, its rule-specific refusal appears beside the field, and the draft is kept. They cover legacy snapshots, persistence through `lanai snapshots` and panel reads, success JSON labels including `null` for unlabeled snapshots, and two snapshots with the same label. Tests also prove that missing, oversized, invalid, edge-spaced, symlinked, and non-regular label metadata falls back to the existing date/time display without losing restore/delete access or blocking a poll; that the first readable label wins between duplicate copies; and that a displayed label never replaces the timestamp target. A label containing path and shell metacharacters remains display data, never a path component or command. Both panel prompts are checked for: a first click that starts nothing, focuses the field, turns the button into Save snapshot and shows Cancel, and a Cancel that turns it back; Save snapshot and Enter submission; no second submission while the prompt's own snapshot runs, with the field still editable and Cancel hidden, including a poll before its job record appears; Cancel, Escape in the open prompt from its field, Save snapshot or Cancel (a second Escape closes the panel), panel close and (daily) section collapse that start nothing and keep the draft; a prompt that stays open through any failed attempt and closes after success; a prompt that closes with its draft kept when its action is hidden or disabled by something other than its own job; one open prompt or armed action at a time among the daily prompt, the setup prompt, Restore and Delete; focus moving to an enabled Take a snapshot, or otherwise the panel, when the prompt closes with focus inside it; a refusal that settles while its prompt is closed reopening it, without moving focus or starting anything, also on the first poll after the panel opens, but not after the user closed the prompt on a refusal already shown, not while Restore or Delete is armed and not while its action is off; distinct accessible names; draft survival across periodic polls, section collapse/expand, and failure; clearing after success without erasing a newer draft; rule-specific feedback; enabled Save snapshot during invalid drafts; and bounds at narrow widths. Labeled Restore/Delete accessible names, confirmation wording, active and unfinished restore wording, same-minute duplicate disambiguation in all of those surfaces, and saved-label and confirmation-note wrapping outside the buttons are checked. No automated test touches the live Windows storage.
